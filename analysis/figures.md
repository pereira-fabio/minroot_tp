# Benchmark Figures — Description and Interpretation Guide

All figures are generated by running from the project root:

```bash
analysis/env/bin/python3 analysis/ploter.py 'results/**/*.json' --out figures/ --format png
```

Results must be placed under `results/k{16,32,35}_mpi_N{1,2,4,8,16}/` with one JSON file
per (algorithm, method, challenge size, node count). Figures are written to `figures/`.

---

## Figure 01 — End-to-End Speedup vs Challenge Size

**File:** `01_speedup_total.png`

Plots `powm_baseline_ms / total_ms` as a function of challenge size (bits) for every
(algorithm, method, rank count) configuration. A speedup > 1 means the attack is faster
than the sequential `mpz_powm` baseline.

- The dashed horizontal line at 1× marks the **breakeven point**.
- Lines below 1× indicate the algorithm is still slower than brute-force powm at that size.
- The x-axis is log₂ (challenge bits); the y-axis is log scale.
- Each line corresponds to one fixed configuration (e.g. k32 sieve 32 ranks).

**What to look for:** the challenge size at which each algorithm crosses the breakeven
line, and how steeply the speedup grows beyond it.

---

## Figure 02 — Reconstruction-Only Speedup vs Challenge Size

**File:** `02_speedup_recon.png`

Same structure as Figure 01, but the speedup denominator is `recon_ms` (reconstruction
phase only) instead of `total_ms`. This isolates the algebraic step — the `MPI_Gather`
and final cube-root product — from the factoring step.

- Reconstruction speedup is typically much higher than end-to-end speedup because the
  factoring phase is the bottleneck at large challenge sizes.
- Useful for assessing whether the reconstruction phase scales correctly with rank count.

---

## Figure 03 — Total Execution Time vs Challenge Size

**File:** `03_total_time_scaling.png`

Log-log plot of `total_ms` (y) vs challenge size in bits (x) for all non-powm
configurations. The sequential powm baseline is overlaid as a dashed line.

- The gap between the powm line and an attack line represents the speedup (or slowdown).
- Both axes are logarithmic. The y-axis uses a 1-2-5 tick progression to make the log
  scale legible (i.e. ticks at 10, 20, 50, 100, 200, 500, 1000 ms).
- Crossing the powm line from above means the attack has become faster.

---

## Figure 04 — Factoring and Reconstruction Scaling

**File:** `04_factor_recon_scaling.png`

Two side-by-side subplots:

- **Left:** `factor_ms` vs challenge size — time spent in the parallel sieve / table lookup.
- **Right:** `recon_ms` vs challenge size — time spent in the `MPI_Gather` and cube-root
  product on rank 0.

Both axes are log scale. This figure shows where each phase dominates. For small challenges,
factoring and reconstruction are both fast; for large challenges, factoring is the dominant
cost and reconstruction grows as O(n) in the challenge bit-size.

## Figure 05 — Timing Breakdown per Challenge Size (11 files)

**Files:** `05_timing_breakdown_{N}b.png`  where N ∈ {256, 512, 1024, 2048, 4096, 6144,
8192, 12288, 16384, 20480, 24576}

Grouped bar chart for a single challenge size. Each group on the x-axis is one
configuration (algorithm + method + rank count). Three bars per group:

- Blue: factoring time (`factor_ms`)
- Orange: reconstruction time (`recon_ms`)
- Green: total time (`total_ms`)

Error bars show the standard deviation across warm benchmark runs. The powm baseline is
drawn as a dashed horizontal line. The y-axis is log scale.

**What to look for:** which configuration comes closest to or beats the powm line, and
the relative sizes of the factoring vs reconstruction bars.

---

## Figure 06 — Reconstruction Phase Breakdown vs Size

**File:** `06_recon_breakdown.png`

Drills into the reconstruction phase for MPI configurations. Three sub-components plotted
vs challenge size for each configuration:

- **local_cbrt:** time for each rank to compute its partial cube-root product.
- **gather:** `MPI_Gather` communication time.
- **combine:** time for rank 0 to multiply the gathered partial products.

All on a log-log scale. Useful for diagnosing whether the gather is becoming a bottleneck
as ranks increase or challenge size grows.

---

## Figure 07 — Prime Load Balance per MPI Rank (11 files)

**Files:** `07_rank_load_balance_{N}b.png`  where N is the challenge size in bits.

Bar chart showing the number of prime factors found by each MPI rank for a given challenge
size. Each subplot corresponds to one (algorithm, method, rank count) configuration.
The dashed horizontal line marks the mean across ranks.

**What to look for:** large deviations from the mean indicate load imbalance — some ranks
finish early and sit idle while others are still sieving. Good load balance means all bars
are close to the dashed line. The sieve partitions the candidate range evenly, so balance
is primarily determined by the statistical distribution of prime factors across the range.

## Figure 09 — Strong Scaling: Time and Speedup vs MPI Ranks (6 files)

**Files:** `09_strong_scaling_k{K}_{method}.png`  
where K ∈ {16, 32, 35} and method ∈ {sieve, table}

Two-panel figure for one (algorithm, method) pair, showing how performance changes as
MPI rank count increases while the challenge size is held fixed.

- **Left panel:** total time (ms, log scale, 1-2-5 ticks) vs rank count (log₂ x-axis).
  Each line is a different challenge size (power-of-2 nominal sizes only: 256, 512, …).
  Lines should slope downward as ranks increase.
- **Right panel:** speedup relative to the minimum rank count (2 ranks).
  The black dashed line is ideal linear scaling. Real lines fall below it due to
  communication overhead, Amdahl's law (non-parallelisable phases), and memory contention.

**What to look for:**
- How close real speedup is to the ideal line (parallel efficiency).
- Whether speedup saturates at high rank counts (sign of a communication bottleneck).
- Large challenges typically show better scaling than small ones because the parallelisable
  fraction of work is larger.

## Figure 10 — Parallel Efficiency vs MPI Ranks

**File:** `10_parallel_efficiency.png`

Parallel efficiency is defined as:

```
efficiency(R) = T(R_min) · R_min / (R · T(R))
```

where `R_min` is the smallest rank count tested. A value of 1.0 means perfect linear
scaling; 0.5 means you need twice as many ranks to get the same speedup as ideal.

Each line corresponds to one (algorithm, method) pair at the largest challenge size
common to all rank counts. The dashed line at 1.0 is the ideal reference.

**What to look for:** how quickly efficiency drops as rank count grows, and which
algorithm/method combination retains the most efficiency at high rank counts.

## Figure 11 — Algorithm Comparison: k16 vs k32 vs k35 (2 files)

**Files:** `11_algorithm_comparison_{method}.png`  where method ∈ {sieve, table}

Two-panel comparison at the maximum available rank count (32 ranks in the standard run):

- **Left:** total time (ms) vs challenge size for k16, k32, and k35. The powm baseline
  is overlaid. Lines crossing the powm line from above mark each algorithm's breakeven.
- **Right:** end-to-end speedup over sequential powm for each algorithm.

**What to look for:**
- k16 is the fastest for small challenges because it uses a precomputed table of only
  6542 primes (fits in L1/L2 cache) and never needs a sieve.
- k32 has a higher overhead but a higher success probability than k16.
- k35 matches the paper's concrete parameters (B = 2^35) and achieves the highest speedup
  at large challenge sizes, but its breakeven is higher (~12 000–17 000 bits depending
  on method).
- The crossover points between algorithms show where it is worth paying the higher overhead
  of a larger smoothness bound.
